# Self-Audit（一致性走查）

> 与 `pre-review` 的分工：那个审**这次改动**（固定点以来的 diff）；这个审**仓库现状**——不针对某次改动，而是问「我们之前写下的东西，现在还是真的吗」。

## 什么时候做

三个触发，满足一个就做：

1. **T3 任务结束时**——大改动之后，被它影响的旧文档最可能失准
2. **每完成 10 个任务**——数 `tasks/` 和 `tasks/_archive/` 下的目录总数（归档过的也算，见 `tasks/README.md` 的「归档」），够 10 个就做一次（做完在 journal 里记一笔，别重复数）
3. **用户说「查一下」**——随时

**不是每次任务都做。** 走查的成本是一整轮，只有「积累了一定量的变化」或「变化足够大」才划算。

## 走查什么

**只查活文档**（`AGENTS.md` / `CONTEXT.md` / `docs/architecture.md` / `docs/commands.md` / `docs/pitfalls.md`）。快照文档（`prd` / `plan` / `journal` / `review` / `research` / 切片）过期不是缺陷，不要去「修」。

逐条**实跑**，不要读一遍觉得「应该没问题」：

### 0. 闸门真的在跑吗

```bash
git config core.hooksPath        # 要输出 .githooks
```

clone 出来的仓库这里多半是空的——`.git/config` 不随仓库走，钩子不挂上，下面所有闸门
**静默失效**，而且没有任何提示。补：`git config core.hooksPath .githooks`。

### 1. `docs/commands.md` —— 每条命令真的能跑

```bash
# 逐条实跑。装依赖那类会改环境的，先看清楚再决定跑不跑
```

- 命令不存在 → 文档错了（改文档）
- 命令存在但报错 → 先分清是环境问题还是文档过时
- 输出格式和文档写的不一样 → 文档过时

### 2. `docs/architecture.md` 的 `## 模块划分` —— 路径与职责

- 表里的路径都存在吗？（`check-gates.sh` 已自动查这条）
- 表里每个模块的**职责**描述，和它现在实际做的事一致吗？——**这条机器查不了，是走查的重点**
- 有没有「实际存在但表里没有」的职责？比如某个模块悄悄承担了它不该承担的

### 3. `docs/architecture.md` 的 `## 接口契约` 与 `## 数据模型` —— 逐条对代码

- 签名对得上吗？
- 不变量还成立吗？（比如「金额用整数存分」——去 grep 有没有人写了浮点）
- 数据模型的字段、关系、归属（谁能读 / 谁能写）还对吗？

**这两节机器完全不查**，是最容易烂的地方。

### 4. `CONTEXT.md` 的术语 —— 逐个 grep

每个术语，在代码里 grep 一遍：

- 术语还在用吗？没人用 → 删掉，或者它已经改名了
- 代码里出现的新概念，术语表里有吗？没有 → 补上
- 术语的定义和代码实际含义一致吗？

### 5. `docs/pitfalls.md` —— 每条「解决」命令真的能跑

这是最实用的一条：坑的记录里那条**可直接粘贴的命令**，现在还能用吗？

- 命令失效 → 坑还在，但解决方式变了 → 更新
- 命令跑不了且问题也不再出现 → 说明这个坑已经被上游修了 → 删掉

### 6. `AGENTS.md` 的 `## 编码规范` —— 还被遵守吗

`pre-review` 的 Standards 轴把「违反仓库写下的约定」当作硬违规，**唯一来源就是这一节**。

- 规范里写的，代码里普遍违反 → 要么改代码，要么规范过时了（规范过时也要改，别留着一条没人遵守的规范）
- 代码里有明显一致的约定但规范没写 → 补上

### 7. `docs/adr/` —— 状态还对吗

- 有哪条 ADR 事实上已经被推翻了，但没标 `Status: superseded by ADR-NNNN`？
- **不要改正文**（它记的是当时的理由），只加状态行

### 8. 模块表是不是宽声明

如果 `docs/architecture.md` 的模块表只声明了 `src` 这类祖先路径，那么「新增模块目录」这条自动检查**是失效的**——表写 `src` 就代表「整个 src 当一个模块」，加多少子目录它都不说话。

项目长大之后，把表拆成具体子模块（`src/auth`、`src/billing`……），让这条检查真正生效。

## 产出

一份**不一致清单**，每条写清：

```
| # | 文档 | 文档怎么说 | 现实是什么 | 怎么办 |
|---|---|---|---|---|
| 1 | docs/commands.md:23 | `pnpm test:e2e` | 该脚本已从 package.json 删除 | 改文档 → 换成 `pnpm test` |
```

**每条必须落到一个动作**，三选一：

- **改文档**——现实是对的，文档过时了（大多数情况）
- **改代码**——文档是对的，代码漂了
- **删掉**——两边都不对，这条记录已经没有意义

**不许出现「待确认」**。真确认不了就升级给人，写清卡在哪。

## 输出格式

```markdown
## 一致性走查（<日期>）

走查范围：commands.md / architecture.md / CONTEXT.md / pitfalls.md / AGENTS.md / adr/

| # | 文档 | 文档怎么说 | 现实是什么 | 怎么办 |
|---|---|---|---|---|
| 1 | ... | ... | ... | ... |

### 一致的部分

- commands.md 的 5 条命令全部可跑
- CONTEXT.md 的 8 个术语全部仍在代码中使用

### 处理结果

- 改文档 3 条 / 改代码 1 条 / 删掉 2 条
```

## 走查之后

**结论要落回仓库**，不能只留在对话里：

- 改动本身按正常任务提交（走 `pre-review`）
- 在 journal 里记一笔：走查日期 + 发现条数 + 处理结果
- 如果发现的是「某个决定已经站不住了」，那是新的架构决策 → 走升级规则 4，别在这里顺手改
