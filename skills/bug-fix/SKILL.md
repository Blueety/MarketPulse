# Bug 修复

> 适用于类型轴 = bug 的任务。规模轴决定要走多少流程，但**闸门 A 与规模无关**：改一个字符修一个偶发竞态，也照样要先有能变红的命令。

## 闸门 A：反馈回路（Phase 1）

**这个 skill 的全部重量在这里。** 后面几步都是机械动作。

如果你有一条**紧的**通过/失败信号（能对**这个** bug 变红），二分、假设检验、仪表化都只是在消耗它而已，你一定会找到原因。没有它，盯着代码看多久都没用。

这一步要**不成比例地投入**。激进一点，别放弃。

### 构造顺序（大致按这个顺序试）

1. **失败的测试**，选一个能触达该 bug 的 seam：单元 / 集成 / e2e
2. **curl / HTTP 脚本**打向正在运行的 dev server
3. **CLI 调用**加固定输入，stdout 与已知良好快照 diff
4. **无头浏览器脚本**（Playwright / Puppeteer）驱动 UI，断言 DOM / console / network
5. **重放捕获的 trace**：把真实的网络请求 / payload / 事件日志存盘，单独喂进代码路径
6. **一次性 harness**：只起系统的最小子集（单服务、mock 掉依赖），一次函数调用就能走到出 bug 的代码路径
7. **属性 / fuzz 循环**：bug 是「有时输出错」就跑 1000 组随机输入找失败模式
8. **二分 harness**：bug 出现在两个已知状态之间（commit、数据集、版本），把「启动到状态 X → 检查 → 重复」自动化，让 `git bisect run` 能跑
9. **差分回路**：同一输入跑旧版 vs 新版（或两套配置），diff 输出
10. **HITL 脚本**：最后手段。必须人工点击时，也要用脚本驱动**人**，让回路保持结构化

回路建对了，bug 就解决了九成。

### 把回路收紧

把回路当产品做。已经有了**一个**回路之后，继续收紧：

- 能更快吗？（缓存 setup、跳过无关初始化、缩小测试范围）
- 信号能更利吗？（断言**那个具体症状**，不是「没崩」）
- 能更确定吗？（固定时间、固定随机种子、隔离文件系统、冻结网络）

30 秒的 flaky 回路约等于没有回路；2 秒的确定性回路是调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发循环 100 次、并行、加压力、缩小时间窗口、注入 sleep。50% 概率的 bug 可调，1% 的不可调——持续提高概率直到可调。

### 建不出回路时

明确停下来说出来，不要默默开始猜。列出你试过什么，然后向用户要：(a) 能复现问题的环境访问权，(b) 一份脱敏的捕获物（HAR、日志、core dump、带时间戳的录屏），(c) 允许临时加生产埋点。

**没有回路，不要进入 Phase 2。**

### 完成判据

Phase 1 完成的标志是：你能说出**一条命令**（脚本路径、测试调用、curl），你**已经至少跑过一次**（贴出调用和脱敏后的输出），并且它：

- [ ] **能变红**：驱动的是真实的 bug 代码路径，断言的是**用户描述的那个症状**，能对这个 bug 变红、修好后变绿。不是「能跑不报错」，是**能抓住这个具体的 bug**
- [ ] **确定**：每次跑结论一样（flaky 的按上面的复现率要求）
- [ ] **快**：秒级，不是分钟级
- [ ] **可无人值守**：Agent 能自己跑；需要人参与时只能走上面第 10 种

如果发现自己**在命令存在之前**就去读代码建理论，**停下**——直接跳到假设，正是这个 skill 要防的失败。

## Phase 2：复现 + 最小化

跑回路，看着它随 bug 出现变红。确认：

- [ ] 回路产生的是**用户**描述的失败模式，不是恰好在旁边发生的另一个失败。搞错 bug = 搞错修复
- [ ] 多次运行都能复现（非确定性 bug 则要求复现率足够高）
- [ ] 已经捕获确切症状（报错文本、错误输出、超时数字），后面要拿它验证修复

### 最小化

变红之后，把复现缩到**仍然会变红的最小场景**。输入、调用方、配置、数据、步骤**一次砍一个**，每砍一刀重跑回路，只留下对失败有承重作用的。

为什么值得做：最小复现缩小 Phase 3 的假设空间，并且直接变成 Phase 5 的干净回归测试。

完成标志是**剩下的每个元素都是承重的**：删掉任何一个，回路就变绿。

## Phase 3：假设

在测试任何一个之前，先产出 **3–5 个排序的假设**。只生成一个假设会锚定在第一个看起来合理的念头上。

每个假设必须**可证伪**：说清它做出的预测。

> 格式：「若 X 是因，则改 Y 会让 bug 消失 / 改 Z 会让它更严重。」

说不出预测，这个假设就是感觉，丢掉或收紧它。

**把排序后的清单给用户看，再开始测。** 用户常有域知识能瞬间重排（「我们刚部署了 #3 的改动」），或者已经排除过某些假设。这是一次便宜的检查点；先按你的排序继续，不要卡住等。

## Phase 4：仪表

每个探针必须对应 Phase 3 里某个具体的预测。**一次只改一个变量。**

工具优先级：

1. **调试器 / REPL 检查**（环境支持的话）。一个断点胜过十条日志
2. **定点日志**，加在能区分假设的边界上
3. 永远不要「全都打日志然后 grep」

**每条调试日志加唯一前缀**，例如 `[DEBUG-a4f2]`。收尾清理就变成一次 grep。没加前缀的日志会活下来，加了前缀的会死——这是好事。

**性能分支。** 性能回归通常不该用日志。先建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测，后修。

## Phase 5：修复 + 回归测试

回归测试**写在修复之前**，但前提是存在**正确的 seam**。

正确的 seam 是指：测试在这个位置上复现的，是 bug 在**调用点实际发生**的模式。如果唯一能用的 seam 太浅（bug 需要多个调用方而测试只有一个、单元测试复现不了触发 bug 的那条链），在那个 seam 上写回归测试只会给出虚假信心。

**不存在正确 seam 本身就是发现。** 记下来：当前的架构阻止了这个 bug 被锁定。提交给下一阶段处理（可能是架构的重构计划）。

存在正确 seam 时：

1. 把最小复现变成该 seam 上的失败测试
2. 看着它失败
3. 应用修复
4. 看着它通过
5. 对原始（未最小化的）场景重跑 Phase 1 的回路

## 闸门 B：清理（提交前必须完成）

- [ ] 原始复现不再复现（重跑 Phase 1 的回路，贴出结果）
- [ ] 回归测试通过（或已记录「不存在正确 seam」）
- [ ] 所有 `[DEBUG-...]` 埋点已删除（grep 前缀）
- [ ] 一次性原型已删除（或移到明确标记的 debug 位置）
- [ ] 正确的那个假设写进了 commit message，让下一个调试的人能学到东西

## Rules

- 先分析，后修改。
- 不在修补循环中引入新依赖。
- 不把「运行失败但推测没问题」当完成。
- 当构建与静态核验通过、但实际行为与预期不符时，禁止仅凭代码推理下结论。必须用运行时取证（远程调试端口 + 真实渲染测量、截图、状态检查）定位真实根因；工具不可用时明确说明缺哪种取证手段，而不是断言「应该没问题」。

## Stop Conditions

- 建不出反馈回路，且已试过上面 10 种构造顺序 → 停下来要环境访问权或捕获物
- 无法复现且无清晰证据
- 修复需要扩大范围 → 按 `docs/agents/任务分级.md` 升档并重新声明
- 第三次尝试仍失败 → 交给架构师做根因分析
- 涉及安全、数据丢失或生产配置 → 先问

## Output

- 根因一句话说明（含最终正确的那个假设）
- 修复的文件和改动摘要
- 验证命令和结果（含 Phase 1 回路的复跑结果）
- 是否需要后续跟进（例如「不存在正确 seam，需要重构」）
