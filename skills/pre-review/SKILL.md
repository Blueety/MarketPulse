# 提交前审查

对某个固定点到 `HEAD` 之间的 diff 做双轴审查：

- **Standards**：代码是否符合本仓库写明的编码规范，外加下面的坏味道基线
- **Spec**：代码是否忠实实现了来源 prd

两轴分开走，**不要合并、不要互相重排**。

## 谁执行

| 档位 | 谁审 | 产出 |
|---|---|---|
| T0 | 不审 | — |
| T1 | 自己审（主线程直接过一遍本 skill） | 报告贴回对话 |
| **T2 / T3** | **独立子 agent** | `tasks/<日期>-<简述>/review.md` |

**T2 / T3 必须换人。** 自审的结构性问题是：审查者和被审查者是同一个——它**已经形成结论**了，而它又恰恰知道「我为什么这么写」，所以看不见「谁还在按老写法用」。

**独立审查者的输入必须自包含。** 给它这几样：

- `tasks/<日期>-<简述>/prd.md` 与 `plan.md`
- diff（`git add -A && git diff --cached <固定点>`，或打包成一个文件）
- **它要当规范来源读的活文档**：`AGENTS.md`、`docs/architecture.md`、`docs/pitfalls.md`、`docs/commands.md`、`CONTEXT.md`、既有测试
- **本次改动的文件清单**（`git diff --cached --stat`）——Docs 维度要判断「改动影响了哪些文档」，没有清单它判不了

**不要给它主线程的会话历史、不要给它「我为什么这么改」的解释。** 给了，它就会继承主线程的结论——那只是换个地方自我确认，不叫独立审查。

> 注意：上面这份清单要**给全**。少了 `pitfalls.md` / `commands.md` / `CONTEXT.md`，Standards 轴找不到全部规范来源，Docs 维度也判不了——那会让它把「我没看到」误报成「没有问题」。

审查者的报告**原文**由被审查方逐字贴进 `review.md`，再按 `skills/receiving-review/SKILL.md` 逐条处理。**轮次上限 2**：两轮还有未解决的 Critical 就停下，升级给人——不要让它俩互相说服。

## 为什么分两轴

一个改动可以通过一轴而挂掉另一轴：

- 每一处都符合规范，但做的不是要的东西 → **Standards 过，Spec 挂**
- 完全照 prd 实现，但破坏了项目约定 → **Spec 过，Standards 挂**

分开报告，才能避免一轴掩盖另一轴。

## 流程

### 1. 钉住固定点

用户给的固定点就是固定点（commit SHA、分支名、tag、`main`、`HEAD~5`）。没给就问。

```
git add -A                        # 先暂存，未跟踪的新文件才会进 diff（**只为出审查用的 diff**，
                                  # 不是提交动作；真正提交仍受 AGENTS.md 的范围白名单约束）
git diff --cached <固定点>         # 固定点 → 索引，就是「当前工作区」的改动
git log <固定点>..HEAD --oneline
```

先确认固定点能解析、diff 非空。引用错或空 diff 应该在这里失败，而不是在两条审查里失败。

**不要用 `git diff <固定点>...HEAD`**：本任务的改动要到提交那一步才落盘，那时 `HEAD` 还停在固定点上，三点写法审出来是空 diff。只有要审的东西**已经提交**了（复审、回溯审查）才用它。

### 2. 出改动摘要

在看细节之前，先出一段人类可读的**改动摘要**：这次改了什么、为什么、影响面。

顺序很重要——**先让人知道「改了什么」，再进入「改得对不对」**。跳过摘要直接逐 hunk 报发现，审查者得在脑子里重建意图，很容易把「故意的设计」当成问题。

摘要不是复述 diff，是意图层面的图景：哪些模块被动了、有没有引入新概念、有没有动公开接口或数据形状。

```
git diff --cached <固定点> --stat
git log <固定点>..HEAD --oneline
```

### 3. 找 spec 来源

按顺序找起源 prd：

1. commit message 里的任务引用
2. 用户作为参数传的路径
3. `tasks/*/prd.md` 里与本次改动匹配的那份（最常见）

找不到就问用户。用户说没有，Spec 轴跳过并报告「无 spec 可比」。

### 4. 找规范来源

仓库里任何写明代码该怎么写的东西：`AGENTS.md`（尤其「编码规范」段）、`docs/architecture.md`、`docs/pitfalls.md`。

**硬违规只能引用写在这里的东西。** 仓库里没写明的，就只能是坏味道（判断题）。这也是为什么 `AGENTS.md` 的「编码规范」段不能留空——留空等于 Standards 轴永远报不出硬违规。

在仓库文档之上，Standards 轴**始终**带着下面的坏味道基线。两条约束：

- **仓库文档优先**：写明的仓库规范永远赢；仓库背书的东西，基线即使会标记它也压下去
- **永远是判断题**：每条坏味道都是带标签的启发式（「疑似 Feature Envy」），不是硬违规。工具已经能查的一律跳过

### 5. 坏味道基线

每条读作 *它是什么* → *怎么修*，拿 diff 去对：

| 坏味道 | 它是什么 → 怎么修 |
|---|---|
| **神秘命名** | 函数 / 变量 / 类型的名字没透露它做什么或存什么 → 改名；想不出诚实的名字，说明设计本身混浊 |
| **重复代码** | 同一段逻辑形状出现在改动里的多个 hunk 或文件 → 抽出共享形状，两边调用它 |
| **依恋情结** | 方法访问别的对象的数据比访问自己的还多 → 把方法搬到它羡慕的那份数据上 |
| **数据泥团** | 同样几个字段或参数一直结伴出现（一个想诞生的类型） → 打包成一个类型，传这个类型 |
| **基本类型偏执** | 用基本类型或字符串顶替一个本该有自己类型的领域概念 → 给这个概念一个小类型 |
| **重复的 switch** | 对同一类型的同一个 switch / if 级联在改动里反复出现 → 换成多态，或两处共用一个 map |
| **霰弹式修改** | 一个逻辑改动迫使 diff 里散落着许多文件的编辑 → 把一起变的东西收进一个模块 |
| **发散式变化** | 一个文件或模块因为几个不相关的原因被修改 → 拆开，让每个模块只为一个原因变化 |
| **夸夸其谈通用性** | 为 prd 里没有的需求加了抽象、参数或钩子 → 删掉，内联回去，等真实需求出现 |
| **过长的消息链** | 调用方不该依赖的 `a.b().c().d()` → 把这一串藏进第一个对象上的一个方法 |
| **中间人** | 一个类或函数大部分只是往下转发 → 砍掉，直接调真正的目标 |
| **被拒绝的遗赠** | 子类或实现类忽略 / 覆盖了继承来的大部分东西 → 去掉继承，改用组合 |

### 6. 两轴分开做

**Standards**：逐文件、逐 hunk 报告 (a) 违反仓库写明规范的地方——引用规范出处（文件 + 那条规则）；(b) 发现的基线坏味道——点名并引用那个 hunk。区分硬违规和判断题：写明规范的违反可以是硬的，基线坏味道永远是判断题，且仓库规范优先。工具能查的跳过。此外逐项检查下表：

| 维度 | 检查项 |
|---|---|
| Correctness | 逻辑是否正确，边界是否覆盖 |
| Performance | 循环里查库 / 发请求（N+1）、无界缓存或列表、没解绑的订阅与定时器、把线性逻辑改成 O(n²) 或整表扫描 |
| Tests | 相关测试是否已运行，是否缺少测试 |
| Security | 是否暴露敏感信息，是否有注入风险 |
| Conventions | 是否符合项目命名、风格和目录约定 |
| Docs | 是否需要更新活文档：README、architecture、commands、CONTEXT.md、pitfalls.md、AGENTS.md |

**Spec**：报告 (a) prd 要求了但缺失或只做了一半的需求；(b) diff 里没被要求的行为（范围蔓延）；(c) 看着实现了但实现方式可疑的需求；(d) **逐条验收标准 → 对应的代码或测试证据**。每条发现引用 prd 的原文。

(d) 是防「勾选式完成」的：**不要根据 `plan.md` 或切片的勾选状态判断完成**——那些勾是 Agent 自己填的，不是证据。每条验收标准给出对应的代码或测试位置（`文件:行号` / 测试名）；给不出来就是没做，直接报缺失。

### 7. 独立期望值预言机（两轴共用的手段）

> 本项目既有方法论：`.workbuddy/memory/MEMORY.md` §4。做 v2 双轴升级时**不得丢**这一节——它就是当年靠它才发现自己的探针口径错了。

**何时用**：断言红了，**或断言全绿但绿得可疑**；改动涉及判定规则 / 数值口径 / 时区 / 分档 / 阈值时几乎必用。

**做法**：不要用被测实现暴露的断言、钩子或格式化函数来产出期望值 —— 那只能证明「实现等于实现」。
换一条**独立口径**算出期望值，再和实际输出逐例对打。

| 被测面 | 独立口径（示例） |
|---|---|
| 浏览器 JS 的时区 / 分档判定 | Python `zoneinfo` 或**显式 UTC 偏移**，独立算出每个时刻的期望档位 |
| 前端渲染的数值 / 百分比 / 单位 | 从原始数据手算（或换一种语言算），不调页面的格式化函数 |
| 阈值 / 告警触发 | 用最小样本手算边界（阈值 ±1 单位）逐个断言 |
| 回填 / 合并 / 去重时序 | 按规格自己排一遍期望序列，不读实现的中间产物 |

**必须覆盖**：① 每个分档的**边界点**（含左 / 不含右各取一次）；② 会让实现「看起来对」的**陷阱时刻**
（夏令时切换、跨日、月初月末、周末、节假日）；③ **争议格** —— 凡规格/表格里两处对不上，都要用独立口径判谁对。

**纪律**：
- 期望值**从规格推导，不从实现反推**（否则把 bug 固化成期望）。
- 断言表达**不变量**（「分档正确」「不溢出」「与同源函数一致」），不锁具体文案或数值。
- **红了先怀疑探针**：探针与被测实现的口径（取整、时区、单位、坐标系、数值精度）必须**显式对齐**；
  出现 1 个索引 / 1 像素 / 1 分钟的级别分歧时，先对齐口径再怀疑实现。
- 探针脚本**不落仓库**（落 `%TEMP%`），结论与实测值写进 journal。

### 8. 汇总

按 `## Standards` 和 `## Spec` 两节分别呈现两份报告。**不要合并或重排**发现，两轴是刻意分开的。

最后给一行小结：每轴各有几条发现，以及**每轴各自**最严重的那条。不要挑一个跨轴的总冠军——那正是分两轴要防的重排。

## 声称完成前（**执行者**自查）

<!-- 这一节是给**执行者**（写代码那一方）的，不是给审查者的。
     审查者不跑测试、不改代码，它只读 diff——所以它不执行这四条，
     它检查的是「执行者有没有把证据列出来」。
     见 skills/receiving-review/SKILL.md 处理后续。 -->

四件事逐条确认，不能跳。这一步是补自动化闸门的缺口——`scripts/check-gates.sh` 能验字段非空，**验不了「命令是否真的跑过」**：

1. **跑过相关测试**：`docs/commands.md` 里对应的那几条，不是「类似的」那几条
2. **手动走过关键路径**：界面 / CLI 类的改动要真的打开看一眼、真的敲一遍；只读代码不算
3. **跑过 lint / typecheck**
4. **要改的文档已改**：README / architecture / commands / CONTEXT.md，按改动性质决定

四条里有任何一条没做，就在报告里写「未运行 + 原因」，不要写成完成。

两条附加要求：

- **必须是本次任务里实跑过的。** 不接受「我之前跑过」「刚才那次算数」「CI 会跑」——改过一行代码，上一次验证就作废。贴出实际命令和输出。
- **子 agent 报回来的「已完成」要独立复核**，不能直接采信。它和主 agent 一样会把自己的推测当结论。

## Output Format

```
## 改动摘要

<这次改了什么、为什么、影响面。一段话，意图层面，不是复述 diff>

## Standards

### 硬违规
- [文件:行号] 问题描述 — 违反的规范出处

### 判断题（坏味道）
- [文件:行号] 坏味道名称 — 引用的 hunk

### 各维度
- [文件:行号] 问题描述

## Spec

### 缺失 / 部分实现
- [文件:行号] 问题描述 — 引用的 prd 原文

### 范围蔓延
- [文件:行号] 做了但没被要求的事

### 实现可疑
- [文件:行号] 问题描述 — 引用的 prd 原文

### 验收标准 → 证据
- [验收标准原文] → [文件:行号] / <测试名> / 无

## Verification

- 已运行: <命令列表>
- 未运行: <命令列表及原因>

## 未判断的

<!-- 你判断不了的条目必须列在这里，**不许留空**（一条都没有就写「无」）。
     写清楚为什么判断不了——看不到依据 / 缺基准 / 超出 diff 范围。
     把「没判断」显式化，读报告的人才能看出盲区在哪。

- [条目] 为什么判断不了

## 小结

- Standards: N 条，最严重 — <一句话>
- Spec: M 条，最严重 — <一句话>
```

## Rules

- 只读，不修改文件。
- 不把风格偏好当 bug。基线坏味道一律标为判断题。
- 不声称测试通过，除非真的运行了。
- 不根据任务勾选状态判断完成。验收标准要落到代码或测试的位置。
- 每条发现必须落到具体文件和行号。
- 两轴结论不合并、不跨轴排序。
- 断言红、或全绿但可疑时，先跑「独立期望值预言机」（§7）再下结论。
