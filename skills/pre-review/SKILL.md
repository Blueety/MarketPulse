# 提交前审查

对某个固定点到 `HEAD` 之间的 diff 做双轴审查：

- **Standards**：代码是否符合本仓库写明的编码规范，外加下面的坏味道基线
- **Spec**：代码是否忠实实现了来源 prd

两轴分开走，**不要合并、不要互相重排**。

## 为什么分两轴

一个改动可以通过一轴而挂掉另一轴：

- 每一处都符合规范，但做的不是要的东西 → **Standards 过，Spec 挂**
- 完全照 prd 实现，但破坏了项目约定 → **Spec 过，Standards 挂**

分开报告，才能避免一轴掩盖另一轴。

## 流程

### 1. 钉住固定点

用户给的固定点就是固定点（commit SHA、分支名、tag、`main`、`HEAD~5`）。没给就问。

```
git diff <固定点>...HEAD      # 三点，与 merge-base 比较
git log <固定点>..HEAD --oneline
```

先确认固定点能解析、diff 非空。引用错或空 diff 应该在这里失败，而不是在两条审查里失败。

### 2. 找 spec 来源

按顺序找起源 prd：

1. commit message 里的任务引用
2. 用户作为参数传的路径
3. `tasks/*/prd.md` 里与本次改动匹配的那份（最常见）

找不到就问用户。用户说没有，Spec 轴跳过并报告「无 spec 可比」。

### 3. 找规范来源

仓库里任何写明代码该怎么写的东西：`AGENTS.md`、`docs/architecture.md`、`docs/pitfalls.md`。

在仓库文档之上，Standards 轴**始终**带着下面的坏味道基线。两条约束：

- **仓库文档优先**：写明的仓库规范永远赢；仓库背书的东西，基线即使会标记它也压下去
- **永远是判断题**：每条坏味道都是带标签的启发式（「疑似 Feature Envy」），不是硬违规。工具已经能查的一律跳过

### 4. 坏味道基线

每条读作 *它是什么* → *怎么修*，拿 diff 去对：

| 坏味道 | 它是什么 → 怎么修 |
|---|---|
| **神秘命名** | 函数 / 变量 / 类型的名字没透露它做什么或存什么 → 改名；想不出诚实的名字，说明设计本身混浊 |
| **重复代码** | 同一段逻辑形状出现在改动里的多个 hunk 或文件 → 抽出共享形状，两边调用它 |
| **依恋情结** | 方法访问别的对象的数据比访问自己的还多 → 把方法搬到它羡慕的那份数据上 |
| **数据泥团** | 同样几个字段或参数一直结伴出现（一个想诞生的类型） → 打包成一个类型，传这个类型 |
| **基本类型偏执** | 用基本类型或字符串顶替一个本该有自己类型的领域概念 → 给这个概念一个小类型 |
| **重复的 switch** | 对同一类型的同一个 switch / if 级联在改动里反复出现 → 换成多态，或两处共用一个 map |
| **霰弹式修改** | 一个逻辑改动迫使 diff 里散落着许多文件的编辑 → 把一起变的东西收进一个模块 |
| **发散式变化** | 一个文件或模块因为几个不相关的原因被修改 → 拆开，让每个模块只为一个原因变化 |
| **夸夸其谈通用性** | 为 prd 里没有的需求加了抽象、参数或钩子 → 删掉，内联回去，等真实需求出现 |
| **过长的消息链** | 调用方不该依赖的 `a.b().c().d()` → 把这一串藏进第一个对象上的一个方法 |
| **中间人** | 一个类或函数大部分只是往下转发 → 砍掉，直接调真正的目标 |
| **被拒绝的遗赠** | 子类或实现类忽略 / 覆盖了继承来的大部分东西 → 去掉继承，改用组合 |

### 5. 两轴分开做

**Standards**：逐文件、逐 hunk 报告 (a) 违反仓库写明规范的地方——引用规范出处（文件 + 那条规则）；(b) 发现的基线坏味道——点名并引用那个 hunk。区分硬违规和判断题：写明规范的违反可以是硬的，基线坏味道永远是判断题，且仓库规范优先。工具能查的跳过。此外逐项检查下表：

| 维度 | 检查项 |
|---|---|
| Correctness | 逻辑是否正确，边界是否覆盖 |
| Tests | 相关测试是否已运行，是否缺少测试 |
| Security | 是否暴露敏感信息，是否有注入风险 |
| Conventions | 是否符合项目命名、风格和目录约定 |
| Docs | 是否需要更新 README、architecture、commands 或 CONTEXT.md |

**Spec**：报告 (a) prd 要求了但缺失或只做了一半的需求；(b) diff 里没被要求的行为（范围蔓延）；(c) 看着实现了但实现方式可疑的需求。每条发现引用 prd 的原文。

### 6. 独立期望值预言机（两轴共用的手段）

> 本项目既有方法论：`.workbuddy/memory/MEMORY.md` §4。做 v2 双轴升级时**不得丢**这一节——它就是当年靠它才发现自己的探针口径错了。

**何时用**：断言红了，**或断言全绿但绿得可疑**；改动涉及判定规则 / 数值口径 / 时区 / 分档 / 阈值时几乎必用。

**做法**：不要用被测实现暴露的断言、钩子或格式化函数来产出期望值 —— 那只能证明「实现等于实现」。
换一条**独立口径**算出期望值，再和实际输出逐例对打。

| 被测面 | 独立口径（示例） |
|---|---|
| 浏览器 JS 的时区 / 分档判定 | Python `zoneinfo` 或**显式 UTC 偏移**，独立算出每个时刻的期望档位 |
| 前端渲染的数值 / 百分比 / 单位 | 从原始数据手算（或换一种语言算），不调页面的格式化函数 |
| 阈值 / 告警触发 | 用最小样本手算边界（阈值 ±1 单位）逐个断言 |
| 回填 / 合并 / 去重时序 | 按规格自己排一遍期望序列，不读实现的中间产物 |

**必须覆盖**：① 每个分档的**边界点**（含左 / 不含右各取一次）；② 会让实现「看起来对」的**陷阱时刻**
（夏令时切换、跨日、月初月末、周末、节假日）；③ **争议格** —— 凡规格/表格里两处对不上，都要用独立口径判谁对。

**纪律**：
- 期望值**从规格推导，不从实现反推**（否则把 bug 固化成期望）。
- 断言表达**不变量**（「分档正确」「不溢出」「与同源函数一致」），不锁具体文案或数值。
- **红了先怀疑探针**：探针与被测实现的口径（取整、时区、单位、坐标系、数值精度）必须**显式对齐**；
  出现 1 个索引 / 1 像素 / 1 分钟的级别分歧时，先对齐口径再怀疑实现。
- 探针脚本**不落仓库**（落 `%TEMP%`），结论与实测值写进 journal。

### 7. 汇总

按 `## Standards` 和 `## Spec` 两节分别呈现两份报告。**不要合并或重排**发现，两轴是刻意分开的。

最后给一行小结：每轴各有几条发现，以及**每轴各自**最严重的那条。不要挑一个跨轴的总冠军——那正是分两轴要防的重排。

## Output Format

```
## Standards

### 硬违规
- [文件:行号] 问题描述 — 违反的规范出处

### 判断题（坏味道）
- [文件:行号] 坏味道名称 — 引用的 hunk

### 各维度
- [文件:行号] 问题描述

## Spec

### 缺失 / 部分实现
- [文件:行号] 问题描述 — 引用的 prd 原文

### 范围蔓延
- [文件:行号] 做了但没被要求的事

### 实现可疑
- [文件:行号] 问题描述 — 引用的 prd 原文

## Verification

- 已运行: <命令列表>
- 未运行: <命令列表及原因>

## 小结

- Standards: N 条，最严重 — <一句话>
- Spec: M 条，最严重 — <一句话>
```

## Rules

- 只读，不修改文件。
- 不把风格偏好当 bug。基线坏味道一律标为判断题。
- 不声称测试通过，除非真的运行了。
- 每条发现必须落到具体文件和行号。
- 两轴结论不合并、不跨轴排序。
- 断言红、或全绿但可疑时，先跑「独立期望值预言机」再下结论（§6）。
