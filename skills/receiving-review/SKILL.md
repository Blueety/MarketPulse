# 处理审查意见

> `skills/pre-review/SKILL.md` 产出的意见落到这里。**两者是两个时刻、两种失败模式**：
> pre-review 防的是「审查做得不够」，这里防的是「审查意见被糊弄过去」。

## 两种失败模式

**表演式附和**：「你说得对，我马上改。」——看起来配合，实际没理解，改完还是错的。

**盲从实现**：审查者说 A，立刻改成 A，**不问为什么**。审查者也会错：他可能不知道某个约束、可能看错了 diff、可能提的只是口味问题。

两种都是**放弃判断**。你的位置比审查者好：你写过这段代码、读过 `prd.md`、知道当初为什么这么写。

## 每条发现必须落到三选一

不能只回一句「已改」。每条都要明确归类：

| 处理 | 要求 |
|---|---|
| **接受并改** | 改完贴出改动位置 + 重跑的验证 |
| **接受但这次不改** | 写清为什么（不在本次范围 / 成本高于收益 / 该另开任务），并记进 journal 的「下一步」 |
| **不接受** | 给**反证**：指出被忽略的约束、贴出代码或文档出处、说明审查者漏了什么。不给情绪，不给「我觉得」 |

**没有第四种**（「嗯，有道理」然后什么都没发生）。

## 什么时候不该逐条改，该退回计划

有些发现不是「这一行写错了」，是「这份计划本身是错的」。逐条改会把握手轮次烧在一份错计划上：两轮改完，同一批问题还在。

出现下面任一条，停手，**提前升级给人**（不烧第二轮），并把「修正后的计划」写进同一次升级消息——人一次批完：

- 同一轴的 ≥3 条发现落在 `plan.md` 的同一节
- 发现指向的是**拆分方式**（两个切片动同一文件 / 切片不垂直 / seam 选错了层）
- 发现要求改 `docs/architecture.md` 的边界（接口形状 / 数据归属 / 依赖方向）——那是升级规则 4，不是 review 能解决的
- 发现说明 `prd.md` 的验收标准本身写错了

这不是第四种归类：每条发现仍然且只仍然三选一。回退改的是**整批在哪一层处置**——先修 `plan.md`，再对着新计划重跑一轮。

## 改的时候

- **同类问题一次扫完**：审查者只看到 diff 里的那一处，同样的毛病往往在别处也有。改之前先搜一遍全仓库。
- **不要顺手改别的**：审查意见之外的重构会污染 diff，让下一轮审查看不出真正改了什么。
- **改完重跑验证**：改一行也算改动，上一次验证作废。贴出新的实跑结果。
- **不接受的要留痕**：写进报告，不要静默跳过——静默跳过等于假装没看见。

## 完成判据

- [ ] 已判断过这批发现落在代码层还是计划层（见上一节）
- [ ] 每条发现都有明确归类（改 / 不改 + 理由 / 不接受 + 反证）
- [ ] 改过的都重跑过验证，且贴出结果
- [ ] 同类问题已全仓库扫过一遍
- [ ] 不接受的已写进报告，不是静默跳过
