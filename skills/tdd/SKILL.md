# 测试驱动

红 → 绿循环。这份文件是让这个循环产出**值得留下的测试**的参照：什么算好测试、测试写在哪、反模式、循环的规则。写测试前和写测试时都要对照，不是写完再回头补。

写测试前先读 `CONTEXT.md`（如果存在），让测试名和接口用项目的领域词；并遵守相关区域 ADR 里的决定。

## 什么算好测试

测试通过**公开接口**验证行为，不验证实现细节。代码可以整个重写，测试不该受影响。好测试读起来像一份规格：「用户可以带有效购物车结账」明确告诉你存在什么能力，而且它不在乎内部结构，所以能扛过重构。

## Seam：测试写在哪

**Seam** 是你测试的那个公开边界：在这个位置观察行为，而不需要伸手进去。测试活在 seam 上，绝不针对内部。

**只在事先约定的 seam 上写测试。** 写任何测试之前，先把要测的 seam 写下来，并让用户确认。没有确认过的 seam，不写测试。你不可能测所有东西，所以事先约定 seam 是让测试投入落在关键路径和复杂逻辑上、而不是每个边界情况上的办法。

问：「公开接口是什么，我们要测哪些 seam？」

如果接口本身的形状有疑问（模块该多深、seam 该放哪、接口该暴露什么），那是另一个问题——交给架构师。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法、或者走侧信道验证（不用接口而直接查数据库）。特征是：重构时测试挂了，但行为没变。
- **同义反复**：断言用和代码相同的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、手工按同样方式导出的快照、常量断言等于自己），所以它靠构造通过，永远不可能和代码意见不同。期望值必须来自**独立来源**：已知良好的字面量、手算的样例、规格。
- **水平切分**：先把所有测试写完，再写所有实现。批量写出来的测试验证的是**想象中**的行为：你测的是东西的**形状**而不是用户可见的行为，测试对真实变化变得不敏感，而且在还没理解实现之前就锁死了测试结构。改为**垂直切片**：一个测试 → 一次实现 → 重复，每个测试都是一发**曳光弹**，响应上一轮循环教给你的东西。

## 循环规则

- **先红后绿。** 先写会失败的测试，然后只写够让它通过的代码。不要预判未来的测试，不要加投机性功能。
- **一次一个切片。** 一个 seam、一个测试、一次最小实现。
- **重构不属于这个循环。** 它属于审查阶段（见 `skills/pre-review/SKILL.md`），不属于红 → 绿的实现循环。

## 和本项目其它部分的衔接

- 验证命令从 `docs/commands.md` 取，不要凭记忆编。
- 新测试放进项目已有的测试目录和命名约定，不另起一套。
- 修 bug 的回归测试写在修复之前，且只在存在正确 seam 时写（见 `skills/bug-fix/SKILL.md` Phase 5）。
- 测试要确定、可隔离、能全量跑。
- 测试名用领域词，让它读起来像规格。
