# 任务目录

## 任务从哪来

复杂任务不是凭空开始的：先在网页对话里把需求聊清楚、压成一份 **Task Handoff**，再复制成本任务的 `prd.md`。交接卡里每一节都标了去处：

- 标 `→ prd.md` 的（Goal / Requirements / 验收标准 / Constraints / Risks）→ 抄进本任务的 `prd.md`
- 标 `→ 长期文档` 的（现状 / 数据 / 术语与决策）→ 进 `CONTEXT.md` 或 `docs/architecture.md`，**不要**再抄进 `prd.md`——活文档和快照混在一起，两边都会过期

够 ADR 三条准入（难以撤销 + 没有背景会困惑 + 是真实取舍）的决策进 `docs/adr/`；不够格的留在 `prd.md` 的 `## 术语与决策`，跟着任务目录走。

## 任务子目录

每个复杂任务创建一个子目录：

```
tasks/<日期>-<简述>/
  prd.md          需求文档
  plan.md         实施计划
  review.md       审查裁决单（只有 T2 / T3 需要）
  journal.md      执行日志
  tmp/            一次性脚本和中间产物（已在 .gitignore 里，闸门 B 收尾时清掉）
```

## 模板目录

`tasks/_template/` 里有五个空白模板。新建任务时从这里复制：

```bash
cp tasks/_template/prd.md tasks/2026-08-04-add-login/prd.md
cp tasks/_template/plan.md tasks/2026-08-04-add-login/plan.md
cp tasks/_template/journal.md tasks/2026-08-04-add-login/journal.md
# 档位是 T2 / T3 时必须（审查由独立子 agent 做，见 docs/agents/任务分级.md）
cp tasks/_template/review.md tasks/2026-08-04-add-login/review.md
# 只有需要拆成多个切片时才用（见下）
cp tasks/_template/slice.md tasks/2026-08-04-add-login/01-schema.md
```

## 什么时候建任务目录

用 `docs/agents/任务分级.md` 的两轴模型判定（规模 × 类型，取更严的那个），不要凭感觉。信号、`怎么量`、阈值都在那份里，这里不复制。

- 两轴都落在免检线内 → **T0**：不建目录、不写 plan，直接改完跑测试
- 介于两条线之间 → **T1**：建目录、写 `plan.md`，不要求 `prd.md` 和 `review.md`。计划落盘是为了派执行者子 agent——它只认文件，对话里的计划传不过去
- 有信号落在升级线 → 建目录
- 升级线 + 涉及公开接口或跨模块 → 建目录，并且 seam 写进 `plan.md`（T2 / T3 随 plan 一次批准，不另设检查点）
- 修 bug 且现象无法稳定复现 → **不看规模，建目录并按 T3 走**

**T2 / T3 还要多一份 `review.md`**（审查裁决单）：这两档的审查必须由**独立子 agent** 做，报告原文贴进裁决单再逐条处理。`check-gates.sh` 会检查它是否存在且填全——见 `docs/agents/任务分级.md` 的「人检查点与独立审查」。

## 大需求拆成多个任务

一个 prd 装不进单个会话时，拆成多个任务文件，每个声明它被谁挡着：

```
tasks/2026-08-04-add-login/
  prd.md            # 总目标
  01-schema.md      # 被谁挡: 无（可立即开始）
  02-api.md         # 被谁挡: 01
  03-ui.md          # 被谁挡: 02
```

切片文件名是 `NN-描述.md`：**1–2 位数字**开头（`01-`、`1-` 都行，分隔符用 `-` 或 `_` 都行），`check-gates.sh` 按这个规则找切片。三位以上数字开头的（`2026-10-31-调研.md`）当普通笔记，不检查——那种文件放 `tasks/` 外面更合适。

每个切片从 `tasks/_template/slice.md` 复制，字段（档位 / 优先级 / 完成后可以看到什么 / 完成标准 / 文件范围 / 被谁挡 / 状态 / 主要提交）都在模板里，`scripts/check-gates.sh` 会校验。两个容易搞错的点：

- **优先级 ≠ 可执行性。** P0 表示重要，依赖关系表示**现在能不能做**。一张 P0 的切片，如果前置还没完成，也要等。
- **任务前沿**：所有前置都已完成的那些切片，才是现在能动的。下一个该做的就是它们里面优先级最高的那个。

### 提交粒度

**一个任务目录对应一个主要提交。** 多切片任务里，每个切片完成时提交一次，把 SHA 回填到该切片的「主要提交」，状态改成 `completed`。

这条不只是习惯：`skills/pre-review/SKILL.md` 要「从固定点到**当前工作区**的 diff」（`git add -A` 之后 `git diff --cached <固定点>`），固定点默认就是**上一个任务的主要提交**。粒度乱了，审查范围就无从确定。

### 决策条目 vs 执行切片

切片只装「已经知道怎么做」的活。若某一步本质是**待决策的问题**——选型、取哪个口径、要不要做、做到多大——别把它硬写成切片：先落一条**决策条目**（问题 + 一段结论 + 依据），拿到结论再拆执行切片。依据是「能不能现在就把问题**精确表述**出来」：

- 能精确表述 → 开（决策条目或执行切片）
- 不能 → 留在**雾区**（`prd.md` 的 `## Not yet specified`），**不要**预切成切片大小的假切片

### 雾区（Not yet specified）

确定在后面、但现在还看不清的东西，写进 `prd.md` 的 `## Not yet specified`：一两行「疑似的问题 + 什么时候回来看它」。它随任务推进会变清晰：每解掉一个决策条目，就回来看有没有能落成新切片/新决策条目的。判据同上——**能不能精确表述**，不是能不能现在回答。

规则：

- 每个切片是**垂直**的（贯穿 schema / API / UI / 测试），不是一个横向的层
- 切片**别落 T3**：规模轴到 `≥5 文件 / 跨会话`（见 `docs/agents/任务分级.md`）就是切太粗，再竖切一刀。垂直切片天然 4 文件左右，落在 T2 —— 别拿 T1 当上限，那和「必须垂直」直接打架
- 每个切片做完都能独立演示或验证
- 「被谁挡」只写真正卡住它的前置切片，没有就写「无」
- 任何前置都做完的切片，就是下一个该做的

## 需求变了怎么办

`prd.md` 是任务开始时的快照，不是活文档。需求后来变了，**先改 `prd.md` 并单独提交**，再继续实现——不要只在新一轮对话里补一句。

理由：`skills/pre-review/SKILL.md` 的 Spec 轴拿 `prd.md` 当基准去查范围蔓延和漏项。基准过期了，这一轴就变成噪音——要么放过真实缺口，要么把正确的实现报成蔓延。

四步：

1. 改 `prd.md`，把变化写进 Requirements / 验收标准 / Out of Scope
2. 检查 `plan.md` 和切片文件是否需要新增或作废
3. 改代码和测试
4. 重新对照完整 `prd.md` 验证旧行为没被破坏

**每次发现需求和实现不一致，都要明确判断方向**：是实现偏离了规格，还是规格已经落后于真实需求。两个方向都合法，但必须说清是哪个。

## 收尾：journal.md 要给出**去向**

`journal.md` 是任务的最后一份文件，也是唯一会被归档、之后没人再读的东西。所以它的两节不是「写点感想」，是**必须分流**：

| 节 | 要求 | 闸门查什么 |
|---|---|---|
| `## 遇到的问题` | 每条带证据：提交 SHA / 闸门输出 / 「重跑了 N 次才过」的那条命令 | 不查（机器判不了「算不算证据」） |
| `## 下次注意什么` | 每条必须有去向，四选一 | **查**：按**条目**判（`→` 写成下一行也算），条目里含 `→` 或「不沉淀」 |
| `## 验证结果` 的 `- 被打回: N 次` | N = `review.md`「逐条处理」的条目数（T1 写 0）。**只有一个定义**：不是「重跑了几次验证」，那个数写在 `## 遇到的问题` 里当证据 | 不查（模板自带这行，闸门不会把它算成一条验证结果） |

去向只有四种，都不在 `journal.md` 里落地：

```
→ pitfalls           顺手写进 docs/pitfalls.md（问题 / 现象 / 原因 / 解决）
→ 任务分级阈值        判据画错了，改 docs/agents/任务分级.md 的数
→ skills/<名>        某个 skill 缺一步，补那个 SKILL.md
不沉淀                只对本次有效
```

为什么要求得这么死：`tasks/_archive/` 在全量自查里是跳过的，`skills/self-audit` 走查的是文档一致性、不读历史 journal。**没有去向的经验等于没写。** 闸门只查形式（有没有写出口），不查内容质量——判质量只会退化成勾选表演。

## 归档

任务 `结束状态` 是 `DONE` 且已经提交之后，把它移进 `tasks/_archive/`：

```bash
mkdir -p tasks/_archive
git mv tasks/2026-08-04-add-login tasks/_archive/
git commit -m "chore: 归档 add-login"
```

**先 `mkdir -p`**：目录不存在时 `git mv` 会把任务目录**改名成** `_archive`——文件被拍平到 `tasks/_archive/` 底下，任务名那层没了。更糟的是拍平之后 `tasks/_archive/` 会被全量自查当归档目录整个跳过，那些文件就再没有全量检查兜着了。

**单独提交，别混进实现提交**——否则 `pre-review` 的 diff 里会多出一堆重命名，掩盖真正的改动。

`tasks/` 只放**在飞的**任务。原因不是整洁，是成本：全量自查逐个任务目录扫，成本随目录数线性增长（本机 20 个目录约 6 秒），而 `tasks/` 只增不减。

归档的语义：

- **全量自查跳过** `tasks/_archive/`——那是已完成、不会再变的快照
- **`--staged` 不跳过**：改到归档里的文件，照样按正常闸门查
- **纯重命名（R100，内容一字未变）不算改动**——否则「归档」这个被推荐的动作本身会
  因为旧格式被判红。移动时顺手改了内容，就照常查。
- 反过来，**拍平归档照样报**：那层的文件从此不在任何全量检查的覆盖里，必须当场拦
- 显式点名也照查：`sh scripts/check-gates.sh tasks/_archive/2026-08-04-add-login`

`_archive/` 自己不是一个任务目录，它下面的子目录才是——往它顶层直接放文件会被 `check-gates.sh` 报错（那正是上面「改名成 `_archive`」的后果）。

## 闸门升级后的存量违规

模板的 `scripts/check-gates.sh` 会随脚手架更新一起进来，而**新规则对历史文件是全红的**：昨天还是零违规，今天可能是几百条。这不是你的代码坏了，是旧任务记录按旧格式写的。

先分类，再选路线——一刀切通常不是最省事的：

| 方案 | 适合 |
|---|---|
| 只归档「纯记录」目录，回填「还在用的」目录（承载验证脚本、被文档引用的） | 想保住手头的工具，其余当作历史快照 |
| 全部归档 | 任务记录已经没有参考价值 |
| 原地回填全部 | 记录还要长期读，且愿意逐文件补 |
| **不加豁免清单** | 这是默认：几百条是「旧格式」不是「不该管」，豁免会让新任务一起失去可信度 |

三条硬规矩：

- **归档前 `mkdir -p tasks/_archive`**（见上一节），否则文件被拍平、整层永久免检
- **改路径引用**：`tasks/<任务>/` → `tasks/_archive/<任务>/`，文档、脚本、`docs/pitfalls.md` 里的命令都要跟着改
- **回填要标注来源**：补的字段只能来自 `git log` 与原文；判断性的内容要写明「这是归档回填，不是当时的记录」，`review.md` 尤其不能伪造一次没发生过的审查

闸门变绿不等于内容正确：它只校验结构，表里某一格被改错它看不出来。回填后自己读一遍。

## 命名规范

```
tasks/2026-08-04-add-login/
tasks/2026-08-05-fix-null-pointer/
```

用 `日期-简短英文描述`，不要用中文或空格。
