# 任务分级

> Agent 在只读分析结束后必须声明档位，只落一行。**T0 / T1 是通知**——发完继续做，人不必在场；**T2 / T3 等 plan 批准**，那一次批准就是本次任务的授权。人随时可以一句话改档。
> 目的：小改不被仪式拖累，大改不漏测试和根因。

## 两轴，分开算

**规模轴**（T0–T3）与**类型轴**（加功能/重构 · bug 可复现 · bug 不可复现）独立判定，取更严的那个。

| | 加功能 / 重构 | 修 bug（有覆盖测试 或 能稳定复现） | 修 bug（无法复现 / 根因未知） |
|---|---|---|---|
| T0 单文件·无行为变化 | 免检 | 免检 | **强制 T3** |
| T1 ≤3 文件·行为局部 | 现行流程，plan 落盘（不要求 review） | 现行流程 | **强制 T3** |
| T2 4 文件 / 跨模块 / 动公开接口 | + seam 确认 | + 闸门 A | T3 |
| T3 ≥5 文件 / 架构 / 跨会话 | + 全部闸门 | + 全部闸门 | + 全部闸门 |

> T0 / T1 / T3 按**文件数**划，T2 按**性质**划——所以 T2 那行必须同时写出「4 文件」：`T1 ≤3 文件` 和 `T3 ≥5 文件` 之间空出的 4 文件正好落在 T2，而 4 也是 6 条信号里文件数的升级线。少了这半句，一个 4 文件、单模块、不动接口的改动就没有归口。

两轴不能合并成一个「大小」，否则会得出荒谬结论：

- 改 20 个文件重命名一个符号 → 规模 T3、类型是纯机械重构 → 要全量测试，但**不需要** seam 确认和根因假设。
- 改一个字符修一个偶发竞态 → 规模 T0、类型是 bug 不可复现 → **按 T3 走**。

## 人检查点与独立审查

档位决定**人要被打断几次**，以及**审查由谁做**。

| 档位 | 人检查点 | 谁审 |
|---|---|---|
| T0 | **0** —— 免检 | 不审（改完跑测试） |
| T1 | **0** —— 收尾看 diff | 自审（`pre-review` 自己过一遍，人只看 diff） |
| T2 | **2** —— 批准 plan + 读裁决单 | **独立子 agent**，产出 `review.md` |
| T3 | **2** —— 批准 plan + 读裁决单 | **独立子 agent**，产出 `review.md` |

T2 / T3 的两次检查点都是**有完整上下文的判断**（批准计划、裁决结果），中间**不再逐闸门打断**——档位、架构、闸门 A、seam 四处声明合进 plan 一次批准。

**为什么 T2 也要独立审查**：T2 的定义是「4 文件 / 跨模块 / 动公开接口」——它的危险不在规模，在**破坏半径超出 diff**。动公开接口时，被影响的调用方不在 diff 里；而**写代码的人恰恰知道「我为什么改这个接口」，所以看不见「谁还在按老接口用」**。T2 看起来像小改动，这正是它最危险的地方。

**T1 才是「自审够」的那一档**：≤3 文件、行为局部、调用方 0–1。

独立审查只覆盖**判断类和证据类**闸门。**授权类不动**：`AGENTS.md` 里那 7 类不可逆的外部动作仍逐次确认，不接受预先授权。

档位声明也是授权类，但它只在 **T2 / T3** 上要人点头——而且那一次点头批准的是 plan（见上面「人检查点与独立审查」），档位合在里面，不额外打断。**T0 / T1 的声明是通知，不是问句**：发完那一行就继续做，人不在场不等。T1 只有 ≤3 个文件，为一次点头停住整个任务换不来信息，只换来「小改动也得盯着」；真做大了，升级规则会要求它停下来重新声明，那时才变成问句。

这条能成立的前提是**底下有机械底线**：`scripts/check-gates.sh --staged` 在提交时数 `src/` 下改了几个文件，≥ 4 而任务目录里没有 T2 / T3 的声明就直接拦下。T0 / T1 不再等人确认，靠的就是这一条兜住「别把 T2 的活说成 T1」。

## 6 条信号

前两条可数，权重最高；中间三条是判断项；最后一条只做粗参考，不单独定档。

| 信号 | 怎么量 | 免检线 | 升级线 |
|---|---|---|---|
| 要动的文件数 | 只读扫描后列出 | = 1 | ≥ 4 |
| 受影响调用方数 | `lsp references` 结果条数 | 0–1 | ≥ 2 |
| 是否动公开接口 / 数据形状 | 读代码 | 否 | 是 |
| 该路径有无现存测试 | 搜测试目录 | 有且当前能跑通 | 无 |
| 行为是否变化 | 判断 | 只改文案 / 格式 / 注释 / 日志文本 | 是 |
| 预估 diff 行数 | 按「要改的文件 × 改动性质」粗估 | ≤ 20 | > 200 |

判据必须来自**量出来的事实**（文件数、references 条数、测试是否存在），不能来自需求文字。「这个很简单」是最不可靠的信号——说这话的人往往还没看代码。

「预估 diff 行数」只做粗参考：它在动手前**原理上量不出来**，写个数字只是逼你把改动规模想一遍。别单凭它定档；真要按它升级，说明你在猜。

**「文件数」这一条在提交时会被机械校验**：`scripts/check-gates.sh --staged` 数这个任务累计改了几个 `src/` 下的文件（从 `plan.md` 进入历史的那次提交算起，拆成两次提交也算），≥ 4 而没有 T2 / T3 的声明就拦下。其余四条判断项（跨模块、动公开接口、行为变化、不可逆性）机器看不见，仍然靠人看 diff。

## 声明格式

一行，禁止展开成段落。写成小作文就是违规。

```
档位: T1 — 2 文件 / 0 调用方 / 行为有变 / 无覆盖测试 / 预估 40 行
```

用户可以一句话覆盖（`T3，我不确定根因`），**以用户的话为准**。

## 4 条升级规则

中途发现判错了，按这几条走，不要重新论证：

1. **实际改动文件数 > 声明文件数** → 停，回到计划阶段重新声明档位，并说明前面的分析漏了什么。升到 T2/T3 时，还要补上那一档要求的东西（任务目录、`prd.md`、独立审查）。声明 T1 却真动了 ≥4 个 `src/` 下的文件时，提交会被闸门直接拦下——不是「混过去就没事」
2. **需要动第 2 个调用方或公开接口** → 升一档。**升到 T1 可以静默继续**；**升到 T2/T3 必须停下来**——那两档有「批准 plan」和「独立审查」两个检查点，静默升档等于绕过它们，而这两条不接受预先授权
3. **修 bug 第一次验证没变绿** → 升 T3，回到闸门 A 造反馈回路。若原先没有任务目录，此时补建

前三条调整**档位**。第 4 条不是升档，是在任务前面**插入一步**：

4. **这次改动引入了项目尺度的决定** → 先做一轮架构设计（`docs/agents/架构师.md` 的「项目尺度架构设计」），更新 `docs/architecture.md`，再出任务计划。

   **谁做**：由**架构师**角色做设计（它的职责第 1 条就是架构设计），产出是四节的**内容**——模块划分 / 接口契约 / 数据模型 / 依赖方向。架构师**不直接改项目文件**，落盘由**执行者**在同一个任务里完成（这也是 `架构师.md` 里「规划与实现分离」的既定约束）。

   满足任一条即算：

   - **新增模块** —— 可判定：要新建的目录不在 `architecture.md` 的模块划分表里
   - 改变模块之间的依赖方向，或引入环
   - 决定或改变**数据归属**（谁拥有、谁能写、别人只能引用 ID）
   - **定下**新的对外接口形状（改**已有**接口是规则 2 的事，两者不同）
   - 改动客户端 / 服务端的分界

   为什么单独一条：前三条管的是「**这次**会做错」，这一条管的是「**边界没定，后面 N 个任务各做各的**」。升档解决不了它——T3 只是把这次做仔细，不会让边界被定下来。

规则 2、3 自动执行。规则 1 必须报告，因为它意味着分析漏了东西。规则 4 要先说明再做，因为它改变的不只是这次任务的前提。

## T0 的含义

T0 免检：不建任务目录、不写 plan、不写 journal、不审查，直接改完跑测试。改个 typo 不该被自己的流程拦住。

**但 T0 的改动照常提交**（一个普通 commit）。下一个任务的审查固定点是「上一个任务的提交」——T0 不提交，它的改动就会混进下一个 T2/T3 任务的审查 diff，被当成「这次多改的东西」。

## 阈值调整

这套线是起始值，按实际分布调。T3 占比长期超过三成，说明线画低了；埋了 bug 到后面才炸，说明线画高了。
