# 决策记录（ADR）

> 记录「为什么这么做」。ADR 不是变更日志，不是任务记录，也不是实现说明。

## 什么时候写

下面三条**同时**满足才写：

1. **难以撤销**：以后改主意的成本很高
2. **没有背景会让人困惑**：未来的读者（或 Agent）看到代码会问「为什么这么写」
3. **是真实取舍的结果**：确实有替代方案，因为具体原因选了现在这个

缺任何一条就不写。容易撤销的决策到时候直接撤销就行；不意外的决策没人会问；没有替代方案的决策只是「照常做」，没有可记录的信息。

## 值得写的典型情况

- **架构形态**：单体 / monorepo / 分层方式
- **带锁定成本的技术选型**：数据库、消息队列、认证服务商、部署目标。不是每个库都算，是换起来要花一个季度的那些
- **边界决策**：哪些数据归哪个模块所有，其他模块只能引用 ID。明确「不做什么」和「做什么」一样有价值
- **刻意偏离常规**：例如「用手写 SQL 不用 ORM」。这类必须写，否则下一个人会来「修好」它
- **代码里看不见的约束**：合规要求、对方 API 的 200ms 上限
- **被否决但有诱惑力的替代方案**：否则半年后会有人再提一遍

## 不该写在这

| 内容 | 该去哪 |
|---|---|
| 实施步骤、文件清单 | `tasks/<日期>-<简述>/plan.md` |
| 反复出现的坑 | `docs/pitfalls.md` |
| 模块划分现状 | `docs/architecture.md` |
| 术语定义 | `CONTEXT.md` |

## 格式

文件放 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md`。

```md
# {决策的简短标题}

{1-3 句：背景是什么、决定了什么、为什么。}
```

一段话就够。价值在于记录**做过这个决定以及为什么**，不在于填满小节。

编号规则：扫 `docs/adr/`，取最大编号 +1。

## 可选小节

只在真正有价值时加，多数 ADR 不需要：

- **Status**：`proposed | accepted | deprecated | superseded by ADR-NNNN`。决策可能被重新讨论时有用
- **Considered Options**：被否决的方案值得记住时才写
- **Consequences**：有非显然的下游影响时才写

## 创建时机

第一次需要时再建 ADR 文件，不要预先占编号。
